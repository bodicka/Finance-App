# Finance App

Это учебный проект, в котором я реализовал веб-приложение для аналитики финансовых данных: от создания серверной части до подключения интерфейса к API и отображения информации на dashboard.

Проект был сделан как практическая работа по изучению современных подходов к разработке: React + TypeScript на фронтенде, Express + MongoDB на бэкенде, а также Redux Toolkit и RTK Query для работы с данными.

---

## О проекте

Finance App — это dashboard для анализа финансового состояния компании. В приложении можно увидеть:

- общий доход и расходы;
- прибыль;
- расходы по категориям;
- ежемесячную и ежедневную динамику;
- список продуктов и транзакций.

Главная задача проекта — не просто создать интерфейс, а понять, как правильно организовать взаимодействие между клиентом и сервером, как хранить состояние приложения и как строить архитектуру данных.

---

Этот проект стал для меня хорошей практикой в нескольких направлениях:

## Как я организовал взаимодействие frontend и backend

Одна из главных задач проекта была в том, чтобы правильно связать клиентскую и серверную части.

На фронтенде я не писал ручные запросы в каждом компоненте. Вместо этого я настроил работу через RTK Query. Это позволило:

- централизованно описать API-запросы;
- не дублировать код для каждого вызова;
- автоматически кэшировать полученные данные;
- проще управлять состоянием загрузки и ошибок;
- получать данные в компонентах через удобные хуки.

На бэкенде я создал отдельные маршруты, которые отдавали нужные данные по запросу клиента. Таким образом, frontend получал информацию из API, а backend был источником данных для интерфейса.

## Работа с RTK Query

Для работы с данными с сервера я использовал RTK Query, потому что это позволило сделать архитектуру более удобной и понятной.

### Что именно я сделал

Я создал API-слой в файле client/src/scenes/state/api.ts и описал там основные запросы приложения:

- getKpis — получение KPI-данных;
- getProducts — получение списка продуктов;
- getTransactions — получение списка транзакций.

Каждый endpoint описан как отдельный запрос с базовым URL, который берётся из переменной окружения.

### Почему RTK Query был полезен

Использование RTK Query дало мне несколько преимуществ:

- не нужно вручную писать состояние загрузки и ошибки для каждого запроса;
- данные кэшируются автоматически;
- компоненты получают данные через готовые хуки;
- код становится чище и проще в поддержке.

### Как я применил это на практике

Я создал хуки:

- useGetKpisQuery
- useGetProductsQuery
- useGetTransactionsQuery

И затем подключал их к компонентам интерфейса. Это позволило получать данные с backend прямо в UI без лишней логики внутри самих компонентов.

## Как я работал с состоянием приложения

В этом проекте я использовал Redux Toolkit в связке с RTK Query.

### Что было настроено

- создан Redux store;
- подключён RTK Query middleware;
- зарегистрирован API reducer;
- включена работа с listeners для обновления данных.

### Почему такой подход был удобен

Это помогло показать, как в реальном проекте выглядит путь данных:

То есть я не просто “взял данные”, а выстроил полноценный поток данных между всеми слоями приложения.

## Как я работал с RTK Query

RTK Query я использовал как основной инструмент для работы с серверными данными. Это позволило мне отказаться от ручного написания одноразовых запросов в каждом компоненте и сделать архитектуру гораздо чище.

### Что я делал на практике

- создавал API-слой через createApi;
- описывал endpoints для каждого типа данных;
- настраивал базовый URL через переменную окружения;
- использовал хуки RTK Query прямо в компонентах;
- работал с кэшем, загрузкой и ошибками без лишнего boilerplate-кода.

### Реальный пример API-слоя

```ts
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";
import { GetKpiResponse, GetProductsResponse, GetTransactionsResponse } from "./types";

export const api = createApi({
    baseQuery: fetchBaseQuery({ baseUrl: import.meta.env.VITE_BASE_URL }),
    reducerPath: "main",
    tagTypes: ["Kpis", "Products", "Transactions"],
    endpoints: (build) => ({
        getKpis: build.query<Array<GetKpiResponse>, void>({
            query: () => "kpi/kpis/",
            providesTags: ["Kpis"]
        }),
        getProducts: build.query<Array<GetProductsResponse>, void>({
            query: () => "product/products/",
            providesTags: ["Kpis", "Products"]
        }),
        getTransactions: build.query<Array<GetTransactionsResponse>, void>({
            query: () => "transaction/transactions/",
            providesTags: ["Transactions"]
        })
    })
})
```

### Какие запросы я делал

- getKpis — для получения KPI данных;
- getProducts — для получения продуктов;
- getTransactions — для получения транзакций.

Каждый запрос был привязан к конкретному backend-роуту и возвращал данные, которые затем я использовал в интерфейсе.

## Как я работал с Redux Toolkit

Redux Toolkit я использовал не как “просто store”, а как инструмент для подключения RTK Query и управления состоянием приложения.

### Что я настроил

- создал Redux store;
- подключил RTK Query middleware;
- зарегистрировал API reducer;
- включил listeners для работы с запросами и обновлениями данных.

### Пример store

```ts
import { configureStore } from "@reduxjs/toolkit";
import { api } from "./api";
import { setupListeners } from "@reduxjs/toolkit/query";

export const store = configureStore({
    reducer: { [api.reducerPath]: api.reducer },
    middleware: (getDefault) => getDefault().concat(api.middleware)
})

setupListeners(store.dispatch);
```

### Что я понимаю под работой со slice в этом проекте

В этом проекте у меня не было большого количества кастомных slice, потому что основная часть данных приходила через RTK Query. Но именно в такой архитектуре я увидел, как удобно делать разделение:

- RTK Query отвечает за получение и кэширование серверных данных;
- Redux Toolkit даёт инфраструктуру для работы со store;
- UI-компоненты получают данные через хуки и уже сами решают, как их отображать.

То есть в этом проекте я не писал сложные slice для каждой сущности, потому что основная логика была сосредоточена в API-слое и в работе с запросами. Но я всё равно понимал, где и как строить состояние приложения и как оно связано с сетевыми запросами.

## Как я принимал запросы с backend и адаптировал их под frontend

Это был очень важный этап. Я брал данные с backend и затем адаптировал их под UI.

### Пример работы с backend

На сервере я реализовал маршруты, например для KPI:

```js
import express from "express";
import KPI from "../models/KPI.js";

const router = express.Router();

router.get("/kpis", async (req, res) => {
    try {
        const kpis = await KPI.find();
        res.status(200).json(kpis);
    } 
    catch (error) {
        res.status(404).json({ message: error.message })
    }
});

export default router;
```

### Что происходило дальше

- backend возвращал JSON с данными из MongoDB;
- RTK Query принимал этот ответ;
- я использовал эти данные в components;
- интерфейс уже отображал готовую информацию в понятном для пользователя виде.

### Как я использовал данные в UI

В компонентах я подключал хук и уже работал с результатом запроса:

```ts
const { data: kpis, isLoading, error } = useGetKpisQuery();
```

Это был практический пример того, как данные с backend превращаются в UI-элементы.
